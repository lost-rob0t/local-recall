* Acceptance criteria
- A user can identify and delete an unwanted capture through CLI/API first; richer UI may follow.
- Deleted records no longer appear in search, summaries, or answers.
- Failed partial deletion is recoverable and never leaves orphaned plaintext.
- Every destructive action requires explicit scope and emits a sanitized audit event.

* Required behavior
- Timeline listing by date, time, application, workspace, and activity cluster.
- Explicit decrypt-on-demand preview for redacted screenshots and text.
- Show capture provenance, redaction findings, model versions, and policy decision.
- Delete individual records, clusters, applications, or time ranges.
- Deletion updates indexes, summaries, citations, and storage references atomically.
- Preview caches remain memory-only or encrypted and expire promptly.

* RAGE iteration 1
** Research
*** Current architecture evidence
- Canonical storage already has a crash-recoverable single-record deletion state: mark the catalog row =deleting=, unlink the encrypted blob, fsync the shard, then remove the catalog row. =get= and day-range candidate enumeration expose only =ready= records.
- The storage catalog deliberately contains only coarse/opaque metadata. Exact timestamps, application/workspace names, OCR, titles, summaries, embeddings, and deletion scope are not catalog columns. Scope selection therefore must happen only after bounded decrypt-on-demand, not by adding plaintext metadata columns.
- Retrieval treats storage as authoritative: semantic hits are intersected with canonical storage candidate IDs and every returned passage requires a still-present encrypted envelope. A stale semantic entry therefore cannot by itself resurrect a deleted record into answers.
- The semantic index is one encrypted authenticated snapshot replaced atomically under an operation lock. It originally supported add/search/rebuild but no record-removal operation.
- Activity clusters/summaries are another encrypted replace-in-full snapshot. =ActivityReconciler= already knows how to regenerate clusters/summaries from a supplied tuple of remaining redacted records and replaces the complete snapshot.
- The authenticated owner-only IPC boundary from #29 already separates capabilities and supplies the correct transport authority for destructive CLI/API calls.

*** External primary-source findings
- SQLite serializes writers and provides atomic database transactions, but WAL mode commits by appending commit records to the WAL; checkpointing later transfers pages into the main database. Therefore application-level logical deletion must not be confused with immediate physical erasure of every prior byte.
- SQLite documents =secure_delete= and =VACUUM= as mechanisms affecting forensic remnants in database pages. Those are relevant to #31 cryptographic/retention deletion, not a justification for widening #30 into physical secure erase.
- SQLite WAL and journal files are part of persistent database state during recovery. Crash safety must preserve the deletion transaction state rather than deleting recovery metadata ad hoc.

*** Adversarial conclusions
1. Rejected: one in-memory "transaction" that mutates catalog, semantic index, activity snapshot, and blobs and rolls back on exceptions. The resources are independent files; rollback after a blob unlink cannot recreate the original ciphertext safely without inventing a second plaintext/ciphertext cache.
2. Rejected: delete blob first without durable intent, then repair derived state. A crash after unlink but before repair creates no durable coordinator evidence.
3. Rejected: store application/workspace/time-range deletion predicates in the plaintext catalog. This violates the catalog leakage boundary from #11.
4. Rejected: treat semantic index removal as the authoritative deletion. Retrieval correctly treats encrypted storage as canonical, so storage visibility/existence must remain authoritative.
5. Accepted: resolve an explicit bounded deletion scope to opaque record IDs while decrypted records are memory-only; record a content-free durable intent; use the already-proven canonical storage deletion state machine for every selected record; then reconcile every derived encrypted snapshot from surviving canonical records; finally clear the durable intent. Crash recovery always resumes forward.

** Design
*** Authority and state ownership
- Storage remains canonical record existence/visibility authority.
- A new deletion coordinator owns orchestration only; it does not duplicate storage crypto, indexing, clustering, answering, or IPC authorization.
- Destructive requests are closed typed scopes: record IDs, activity cluster ID/source IDs, application, or bounded time range. Empty/implicit "everything" scopes are invalid in #30.
- Scope resolution uses bounded candidate enumeration + decrypt-on-demand and keeps selected plaintext only for the operation lifetime.
- Once canonical deletion begins, no later cleanup failure is allowed to resurrect a selected record.

*** Forward-only deletion state machine — refined after storage audit
The initial five-phase hidden/blob split would duplicate the storage state machine. The repository already has a stronger per-record crash-safe sequence (=ready -> deleting -> blob unlink/fsync -> catalog removal=). Reuse it rather than introduce a second visibility authority.

1. =planned=: an owner-only content-free deletion journal durably binds an opaque request ID to the exact selected record UUIDs.
2. For every selected UUID invoke the existing idempotent canonical storage delete. A crash here leaves the journal =planned=; storage recovery completes any per-record =deleting= state, and coordinator retry safely repeats already-completed deletes.
3. =records-deleted=: written only after every canonical delete succeeds. At this point retrieval cannot newly load those records even if derived snapshots are stale.
4. Remove the IDs from the encrypted semantic snapshot and reconcile the encrypted activity snapshot from surviving canonical records.
5. =derived-reconciled=: written only after both derived-state operations succeed.
6. Clear the journal and fsync its owner-only directory.

A crash at any phase resumes forward. No rollback makes a deleted record visible again merely because later derived-state repair fails. This avoids a catalog migration/version bump and preserves #11's proven storage recovery logic.

*** Privacy invariants
- Timeline list output may expose only user-requested redacted fields and provenance through the authenticated query capability; status/audit remain content-free.
- Screenshot/text preview is explicit decrypt-on-demand, bounded, returned only through the owner-authenticated query path, and not cached in plaintext.
- Destructive audit events contain operation/request ID, scope class, selected record count, outcome/reason, and timing only; never application names, workspace names, OCR, titles, record contents, prompts, screenshot bytes, or raw scope text.
- The deletion coordinator never writes decrypted records, previews, or scope metadata to temporary files.
- Existing #31 remains owner of cryptographic deletion/key destruction/retention secure erase. #30 guarantees logical inaccessibility plus encrypted blob removal and derived-state cleanup.

*** Race/failure analysis
- Concurrent retrieval started before canonical deletion may hold an already-decrypted working copy. A post-decrypt canonical-visibility recheck is required before returning a passage/preview.
- Stale semantic hits are harmless only while retrieval intersects with canonical ready records; tests must lock this invariant.
- Activity snapshot replacement is atomic but can fail; the deletion journal remains durable and deleted records remain unavailable until retry succeeds.
- Cancellation before journal admission has no effect. Cancellation after canonical deletion begins cannot roll back visibility; the durable journal allows later recovery to continue cleanup.
- Duplicate delete requests must be idempotent by selected record identity; one active journal transaction is allowed at a time.
- A stale journal temporary file must not permanently wedge recovery; journal write/recovery tests must cover interrupted replacement.

*** Migration/configuration
- No plaintext content columns are permitted.
- The refined design requires no catalog migration: durable transaction metadata lives in a bounded owner-only content-free journal containing only opaque request/record identifiers and a closed phase/version.
- No new remote provider/network dependency.
